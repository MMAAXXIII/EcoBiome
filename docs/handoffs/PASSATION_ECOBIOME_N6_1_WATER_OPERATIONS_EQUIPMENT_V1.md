## User-visible scope

N6.1 makes the aquatic-environment view operational in three additional areas:

1. real fill level;
2. water-exchange interventions;
3. per-environment equipment inventory.

## Nominal capacity versus current water volume

The UI no longer treats one `volume_liters` number as both tank capacity and current water volume.

The local projection exposes:
- `capacity_liters`: nominal physical capacity;
- `current_volume_liters`: current water volume derived from project events;
- `fill_percent`: `current_volume_liters / capacity_liters * 100`;
- `volume_liters`: retained as a backward-compatible alias of nominal capacity.

For newly created environments, nominal capacity is stored as static container topology metadata using normalized decimal text. Dynamic water volume remains outside topology.

For N6 V1 projects created before this field existed, the earliest canonical water-volume observation is used as the compatibility fallback for nominal capacity.

## Fill-level editing

The `Remplissage` control records the requested level as a new N5 canonical water-volume observation.

It does not mutate an earlier observation. This preserves chronology and allows later reconstruction of level changes.

The tank visualization uses the persisted/derived fill percentage instead of decorative hard-coded percentages.

## Water exchange

The `Changement d'eau` control records:
- removed volume;
- replacement volume;
- optional user note;
- occurrence time generated by the local API.

The API constructs an N4 `WaterExchangeInterventionV1` and freezes it through `build_canonical_water_exchange_event_v1` as an N5 canonical intervention event.

Current volume is reconstructed chronologically:
- an explicit water-volume observation resets the known current volume;
- each later water-exchange intervention applies `replacement - removed`.

The API rejects:
- a zero/zero exchange;
- removal larger than current water volume;
- a resulting volume below zero;
- a resulting volume above nominal capacity.

Replacement-water chemistry is deliberately not invented. N6.1 records an empty replacement composition and exposes `composition_status = unknown`. Therefore the UI warns that chemical concentrations are not automatically recalculated from the water exchange yet.

## Equipment inventory

Equipment is project topology/configuration, not scientific evidence and not a dynamic measurement.

N6.1 stores each user equipment item as an N4 `FunctionalSystemV1` attached to the water zone and tagged with project-property schema `ecobiome-user-equipment-v1`.

Supported inventory categories:
- water pump;
- air pump;
- lighting;
- heater;
- filter;
- CO2 system;
- sensor/probe;
- other.

Common fields:
- user label/name;
- manufacturer;
- model;
- electrical power in W;
- daily runtime in h/day;
- in-service date;
- notes.

Optional equipment-specific fields:
- nominal flow in L/h for pumps/filtering;
- spectrum/lighting characteristics for lighting.

Numeric equipment properties are stored as normalized decimal strings in canonical profile properties, never as native JSON floats.

The UI derives, when power and daily runtime are both known:
- Wh/day;
- kWh/year.

Multiple items of the same category are admitted, so several pumps or several lamps can be represented separately.

N6.1 V1 supports add/list/delete. Editing an existing item in place is intentionally deferred; a mistaken item can be deleted and re-added without introducing a silent partial mutation contract.

## Validation policy

The N6.1 integration launcher must:
1. require the exact N5 branch/HEAD;
2. require staging to be empty;
3. verify the complete validated N6 V1 candidate identities before writing;
4. require DashboardView and WaterTankViz to be clean tracked baseline files before extending them;
5. back up every overwritten path;
6. apply only the N6.1 scope;
7. run Python compilation, Ruff, mypy, targeted N6 + N6.1 tests and full pytest;
8. run frontend TypeScript typecheck and Vite production build;
9. run `git diff --check`;
10. keep staging empty;
11. rollback N6.1 modifications byte-for-byte on failure while preserving the previously validated N6 V1 working tree;
12. produce a complete audit ZIP outside the repository.

No stage, commit, push, merge, rebase, reset, checkout, provider call, or Scientific Foundation migration is authorized by this gate.

## Known limitations after N6.1

- replacement-water composition is not yet captured in the water-exchange form;
- water-exchange chemistry is therefore not automatically propagated;
- equipment schedules are represented only by average hours/day, not detailed timers or weekly calendars;
- lighting spectrum remains descriptive text, not yet a normalized spectral power distribution;
- equipment inventory does not yet feed automatic thermal, hydraulic, electrical, or reliability diagnostics;
- equipment edit-in-place is deferred;
- no cost-per-kWh model is applied yet.

Do not extend beyond this scope without a separately reviewed step.
